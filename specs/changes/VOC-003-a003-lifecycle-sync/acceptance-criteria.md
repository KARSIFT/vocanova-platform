# Acceptance Criteria

## VOC-003-AC-01 — Exact lifecycle record

The canonical state records both distinct exact SHAs, the approved/adopted tree, real
timestamps, all supplied GitHub evidence, successful post-merge validation, and active
A-003 authority.

## VOC-003-AC-02 — Frozen body integrity

The A-003 substantive body SHA-256 remains
`ad05cc8c92047002288245574bc3b76e1cce6f54d43805039ad53393534af4e7`.

## VOC-003-AC-03 — Active authority consistency

Current guidance says routine R3 has no standing technical-steward or founder
approval merely because it is R3, R4 founder authority is unchanged, and EHR is
exceptional only.

## VOC-003-AC-04 — Historical preservation

The original appointment identity, dual-capacity history, and one-time VOC-002
approval evidence remain preserved; the approval is exhausted and non-reusable.

## VOC-003-AC-05 — Operational non-activation

Automatic/autonomous merge, RL1/RL2 technical activation, production deployment, and
autonomous production release remain disabled or unimplemented; DOC-17 and DOC-18
remain unadopted.

## VOC-003-AC-06 — Fail-closed validation

The required unit suite and governance validators pass the canonical state and reject
missing/conflated evidence, authority rollback, migration reuse, routine EHR/steward
restoration, false technical activation, false DOC adoption, or frozen-body changes.

## VOC-003-AC-07 — R4 and publication boundary

The classifier detects R4. The branch may be pushed and a draft PR opened, but it is
not merged and no founder approval is requested before exact-SHA independent review.
